# Audisor Web — WebContainer deployment (in-repo, not published)

> **Status: standalone development harness.** `host/` is retained solely
> as proof code for booting the whole Audisor web app inside a
> WebContainer. The **product path** is the in-app **Web Runtime**
> feature (`web/src/features/web-runtime/`), which runs a *selected
> project* (bundled sample or imported folder) inside a WebContainer —
> no Audisor-inside-Audisor recursion. See "Web Runtime post-build
> validation gate" below for its mandatory after-build check.

Runs the `web/` app inside a **WebContainer** — an in-browser Node.js
runtime — served entirely from this repository. Nothing here is uploaded
to StackBlitz, CodeSandbox, GitHub, or any other external service;
**publishing requires separate explicit approval**.

## Honesty contract (read first)

- The app talks **only to the real assistant backend** you configure.
- No backend configured, or backend unreachable → the app renders its
  normalized **"unavailable"** state. Nothing substitutes fake responses.
- A malformed backend URL renders a normalized **"configuration"** error.
- The only fake provider that exists anywhere is the **server-side**
  `fake-deterministic` provider: a backend operator must opt into it
  (`AUDISOR_PROVIDER=fake-deterministic`, development/demo use), and the
  UI badges its output honestly as `fake-deterministic`. Production
  deployments must not enable it. This host adds no fake path of its own.

## Layout

```
webcontainer/
  host/                   # Vite app that boots the WebContainer
    public/files.snapshot.json   # generated by snapshot.mjs (git-ignored)
  scripts/snapshot.mjs           # packs web/ into the mountable snapshot
  scripts/postbuild-validate.mjs # post-build fixture validation gate
  fixtures/postbuild.fixture.json
```

## Run instructions

Prerequisites: Node.js 20+, npm, a Chromium- or Firefox-family browser,
and internet access (the in-container `npm install` downloads from the
npm registry).

```powershell
cd webcontainer\host
npm install          # host dependencies (@webcontainer/api, vite)
npm run snapshot     # regenerate after ANY change under web/
npm run dev          # serves the host on http://localhost:5174 (or next free port)
```

Open the printed `http://localhost:…` URL, optionally paste a backend
URL, and click **Boot WebContainer**. The host mounts the snapshot, runs
`npm install` and `npm run dev` inside the container (first boot takes a
few minutes), then shows the app preview in an iframe.

## Required WebContainer headers / configuration

WebContainers need **cross-origin isolation** (SharedArrayBuffer). The
host page must be served with:

```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

`host/vite.config.js` sets both for `npm run dev` and `npm run preview`.
The host refuses to boot (with an explicit on-page error) if the page is
not cross-origin isolated — e.g. when opened from `file://` or a static
server without these headers.

If the preview iframe is ever blocked under `require-corp`, switch
`Cross-Origin-Embedder-Policy` to `credentialless` in
`host/vite.config.js` (supported fallback in Chromium-family browsers).

## Backend connection instructions

1. Run the real backend (`openai_project/assistant_backend`) somewhere
   the browser can reach. Use **HTTPS** for anything hosted; plain
   `http://127.0.0.1:8799` is acceptable only for local development.
2. Allow the preview origin. After boot, the host displays the exact
   preview origin (unique per boot, e.g.
   `https://…webcontainer-api.io`). Add that **exact** value to the
   backend's allow-list — wildcards are rejected by design:

   ```powershell
   $env:AUDISOR_CORS_ORIGINS = '<exact preview origin shown by the host>'
   .\run-dev.ps1 -Model qwen2.5-coder:7b
   ```

3. Paste the backend URL into the host's input **before** clicking Boot.
   It is written to `.env.local` inside the container as
   `VITE_ASSISTANT_API_URL` (see `web/.env.example` for the rules).
4. Authentication: the shipped `DevelopmentAuthProvider` accepts the
   `x-audisor-dev-user` header only when `AUDISOR_ASSISTANT_ENV` is
   `development` (default) or `test`. A production backend rejects all
   requests until a real auth provider is wired — that decision is out of
   scope here.

Known limitation (documented, not hidden): Chrome's Private Network
Access policy may block requests from the public WebContainer preview
origin to a loopback backend (`127.0.0.1`). If that happens, the app
shows its normalized "unavailable" state; use a non-loopback (HTTPS)
backend URL instead.

## Post-build validation gate

After any production build of the web app, run:

```powershell
cd webcontainer\host
npm run validate:postbuild
```

The validator (`scripts/postbuild-validate.mjs`) uses the synthetic
fixture `fixtures/postbuild.fixture.json` to prove, against the real
built artifact:

1. the build succeeds with `VITE_ASSISTANT_API_URL` baked in;
2. `dist/index.html` exists and references hashed assets;
3. the configured backend endpoint reaches the bundle;
4. no forbidden markers leak into `dist/` (no hardcoded dev backend URL,
   no env literals, no identity header in the HTML);
5. `dist/` serves correctly under the COOP/COEP isolation headers;
6. rebuilding **without** the variable removes the fixture origin
   (relative endpoint restored — no stale baking).

Exit code 0 = all assertions passed. The log is written to
`TempProof/webcontainer-deploy/postbuild-validate.txt`.

## Web Runtime post-build validation gate

The in-app Web Runtime feature has its own **mandatory** after-build
gate. After any production build of the web app, run:

```powershell
cd web
npm run validate:webruntime
```

The validator (`scripts/webruntime-postbuild-validate.mjs`) uses the
synthetic fixture `fixtures/webruntime-postbuild.fixture.json` to prove,
against the real built artifact:

1. a clean production build succeeds (no `VITE_ASSISTANT_API_URL` in the
   environment);
2. `dist/index.html` exists and references a hashed JS entry;
3. the feature marker (the sample project's package name) lives **only in
   a lazy chunk** — no chunk referenced by `index.html` contains it, so
   WebContainer code loads only when the feature is opened;
4. the feature UI markers ("Sample project", "Open project folder")
   shipped in the bundle;
5. forbidden markers are absent from every text file in `dist/` (no
   dev-backend URL, no baked env value `VITE_ASSISTANT_API_URL=http…`, no
   external publishing endpoints). `stackblitz.com` is vendor-scoped:
   the string unavoidably ships inside `@webcontainer/api` itself (a
   StackBlitz product), so it is allowed only in the lazy chunk carrying
   the library's own signature — anywhere else fails;
6. `dist/` serves correctly under the COOP/COEP isolation headers
   (required for `crossOriginIsolated` — production hosting must send
   both headers; `web/vite.config.ts` covers dev/preview).

Exit code 0 = all assertions passed. The log is written to
`TempProof/web-runtime/webruntime-postbuild.txt`.

Note: the assistant gate's fixture marker is `VITE_ASSISTANT_API_URL=http`
(a baked *value* leak always includes the value after `=`); the Web
Runtime feature legitimately contains the bare literal
`VITE_ASSISTANT_API_URL=` for its in-container `.env.local` write.
